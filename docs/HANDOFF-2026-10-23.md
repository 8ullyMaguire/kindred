### Second batch (the experiment that found the real defect)

- **33 — `signal.SeedAgreement`.** Every tag signal scored against the BEST
  seed; with the twenty seeds the evaluator passes, that lets a work hitting one
  fandom rank beside one hitting most. The new signal averages each seed's
  IDF-weighted coverage *including zeros* (perfect on 1 of 4 = 0.25, partial on
  all 4 = 0.625), and refuses to run on fewer than two usable seeds.
- **The evaluator was blind.** `kindred eval` built its engine without the
  document-frequency table, so `idf_overlap` and `seed_agreement` skipped for
  every candidate. Five runs came back byte-identical and read as "the new
  signal changes nothing". Fixed, plus `eval_runs.degraded` (migrated in place)
  and `--tune`, so an ablation is a flag rather than a rebuild.
- **Neighbourhood was 100× out of scale.** A live item's evidence showed
  `neighbourhood 123.431 @ 0.32 → 39.5` against `tag_overlap 0.222 → 0.05`. One
  unbounded signal decided the ranking, which is why no tune could matter. It
  now saturates into `[0,1)` via `raw/(raw+100)`.
- **Pool recall.** `--pool-depth N` asks for N ids, scores the first k, and
  counts held-out works in the whole list. Shown on `/eval` as "Pool recall".
- **"Signals blind" honest for legacy rows.** An empty cell now renders "not
  recorded" (the column did not exist) and `all` renders "none"; the first
  version printed "none" for runs that predate the column.

## The numbers (38 readers / 495 held-out works, same split every time)

| run | change | recall@10 | ndcg@10 | coverage |
|-----|--------|-----------|---------|----------|
| 2-3 | baseline, IDF signals blind | 0.0067 | 0.0096 | 0.0789 |
| 4 | control: seed_agreement weight 0 | 0.0067 | 0.0096 | 0.0789 |
| 5 | treatment: seed_agreement 0.10 | 0.0067 | 0.0096 | 0.0789 |
| 6 | neighbourhood weight 0 (ordering test) | 0.0035 | 0.0060 | 0.0526 |
| 7-8 | neighbourhood saturated to [0,1) | 0.0056 | 0.0101 | 0.0789 |

**Run #8 also measured the ceiling: `pool recall@1000 = 0.0284`.**

Read that as: even a perfect ranking of the thousand candidates the engine
considers could find at most 2.8% of held-out works (random chance would be
0.9%). The current recall@10 of 0.0056 is a fifth of what the pool allows.

Two conclusions, both measured rather than argued:

1. **Ordering does matter** — run #6 shows recall halving when the strongest
   signal is switched off.
2. **Ordering matters five times less than candidate generation.** No weighting
   work can exceed the pool. The remaining opportunity is in enumeration.

Run #7's recall is one hit lower than baseline (3 → ~2.8 of 495) with NDCG up
0.0005. At 495 held-out works that is not a verdict; the scale fix was kept
because it makes the weights meaningful and the ranking metric improved. Say so
rather than claiming a win.

## Next unit, by evidence

**Candidate generation.** Concretely, in order of cost:

1. **Measure where candidates come from.** `poolFor` unions tag-neighbours and
   collab. Instrument each source's contribution to pool recall (a per-source
   count in `meta`), so the next decision is about the source that is failing
   rather than about the union.
2. **#11 — embeddings as an enumeration source.** The 634,232 × 32 matrix
   already exists and already scores at weight 0.10; it is used only as a
   *scorer*, never as a *finder*. A nearest-neighbour pass over it would add a
   candidate source that does not depend on tag co-occurrence at all — the one
   thing the current pool cannot do. Memory is the decision: ~81 MiB resident.
3. **Then** re-tune. With the pool wider, the weights start to matter, and
   `--tune` + `--pool-depth` make each attempt one 6-minute run.

Reproduce the baseline in one command:

```bash
ssh thinkcentre 'sudo timeout 2400 kindred eval \
  --corpus /home/alvaro/kindling-data/ao3_metadata.db \
  --db /var/lib/kindred/kindred.db \
  --users 40 --n 10 --pool-depth 1000'
```

An ablation is a stored tune plus a flag:

```bash
SPEC='collab=0.125,embedding=0.07812,idf_overlap=0.09375,neighbourhood=0,...'
ssh thinkcentre "sudo kindred tune --corpus <mirror> --db <state> \
  --name no_neighbourhood --set '$SPEC'"
ssh thinkcentre "sudo timeout 2400 kindred eval --corpus <mirror> --db <state> \
  --users 40 --n 10 --tune no_neighbourhood"
```

## Gotchas for the next session

- `kindred eval` and `kindred tune` both need explicit `--corpus` AND `--db`;
  they do **not** read the systemd unit's `Environment=`. The state DB is
  root-owned, so `sudo`.
- A stored tune must **sum to 1.0** (the built-in default sums to 1.58), so an
  ablation has to be renormalised by hand before `--set` accepts it.
- `signal.Neighbourhood` memoises vote maps in a process-global LRU keyed by
  seed tags + limit only. Tests sharing a seed-tag set share a vote map.
- Deploy order: commit everything, then deploy. Editing a file while a deploy
  runs makes the provenance gate report DRIFTED at the end (it compares the
  binary's embedded revision with HEAD).
- Never run two deploys at once: the behaviour gate probes the live port and the
  second deploy stops the service mid-probe (~26 checks come back UNREACHABLE).
